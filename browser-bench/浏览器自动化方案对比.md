# 浏览器自动化方案对比（Agent 控制浏览器）

> 整理时间：2026-09-05
> 目标场景：内网环境部署，供 codeagent2.0（opencode 内核）/ codeagent3.0（claude code 内核）调用
> 环境约束：无外部 API key、无外网模型服务、内置文本模型 GLM-5.2、视觉模型 qwen3.6-VL

---

## 一、方案全景

Agent 控制浏览器有两条技术路线：

| 路线 | 调用方式 | 代表 | 特点 |
| --- | --- | --- | --- |
| **Skill（CLI 驱动）** | Agent 通过 Bash 调用命令行 | agent-browser、playwright-cli | 无需 MCP 客户端支持，任何能跑 shell 的 agent 都能用 |
| **MCP Server** | Agent 通过 MCP 协议调用工具 | @playwright/mcp、chrome-devtools-mcp、puppeteer MCP | 工具调用结构化，错误反馈更规范，是 2026 年的主流生态 |

两者并不互斥：MCP server 通常也提供 CLI 包装（playwright-cli 就是 @playwright/mcp 的命令行版）。

### 关键分野：Agent 怎么"看见"页面

这是选型的**第一决策点**，直接决定 token 成本和成功率：

- **无障碍树（a11y tree）路线** — 把页面转成结构化文本：`button "查询" [ref=e3]`。Agent 用 ref 操作元素，**不需要视觉模型**，token 消耗低（单次快照 400–700 token），页面改 CSS 也不影响。
- **截图 + 视觉路线** — Agent 看图再猜选择器。强依赖视觉模型能力，token 成本高（一张截图通常 1000+ token），CSS 类名一变就失效。

**本环境结论：必须走 a11y 树路线。** 视觉侧只有 qwen3.6-VL，走截图路线既贵又不可靠。

## 三、内网部署专项评估

这是本次选型的核心约束，逐项对照：

| 内网关切点 | agent-browser | @playwright/mcp（含 CLI 版） | 说明 |
| --- | --- | --- | --- |
| 离线安装 | 需在外网机 npm 打包后拷贝 | 同左 | 两者都无"官方离线安装包"，需自行封装 |
| 浏览器二进制分发 | Chrome 152 约 **429 MB**（下载包 193 MB），存于 `~/.agent-browser/browsers/` | Chromium headless-shell 约 **115 MB**（下载包），存于 `%LOCALAPPDATA%/ms-playwright/` | Playwright 体积小得多 |
| **免分发浏览器** | `--executable-path` 指向内网已有 Chrome/Edge，或 `--auto-connect` 接管现有浏览器 | 可通过 `channel` / `executablePath` 指定 | **内网机器普遍已装 Chrome/Edge，可省去数百 MB 分发** |
| 浏览器路径可定制 | `AGENT_BROWSER_EXECUTABLE_PATH` | `PLAYWRIGHT_BROWSERS_PATH` 可指定缓存目录 | 都能放进统一目录便于打包 |
| 登录态保持 | `--session-name` 自动持久化、`auth save` 存账号密码自动登录 | `state-save`/`state-load` 存取 storage state | 两者都能解决内网系统登录问题 |
| 内网代理 | 支持 `--proxy` 及 `HTTP_PROXY`/`NO_PROXY`/`--proxy-bypass` | 走 Playwright 的 proxy 配置 | 均可 |
| 离线文档 | **内置 `skills get core --full`，完全离线** | 依赖在线文档 | 内网无法查文档时，agent-browser 明显占优 |
| 本地 HTML 文件 | **支持 `file://`** | **封禁 `file://` 协议**（Playwright MCP 安全策略） | 已实测确认：playwright-cli 打开 file:// 直接报 `Access to "file:" protocol is blocked` |
| MCP 原生支持 | 无 MCP server 模式，只能走 Bash | **原生 MCP stdio** | 若 agent 客户端 MCP 支持完善，后者集成更顺 |

## 四、推荐结论

### 首选：@playwright/mcp（走 MCP 路线）

**理由**：
1. **生态与稳妥性最好** —— Microsoft 官方维护，工具数 22 个覆盖全面，是 Claude Code / Cursor / Copilot 等 15+ 客户端的默认推荐，踩坑资料最多，内网排障时有据可依。
2. **a11y 树优先** —— 不依赖视觉模型，契合本环境视觉能力偏弱的现状。
3. **三引擎支持** —— 除 Chromium 外还能跑 Firefox/WebKit，内网若有多浏览器兼容性验证需求可直接覆盖。
4. **登录态可持久化** —— 内网系统普遍需要登录，storage state 存取是刚需。
5. **浏览器体积小** —— 分发包比 agent-browser 小近 300 MB。

**注意点**：
- 不支持 `file://`，本地 HTML 一律挂到内网 HTTP 服务上访问。
- 快照落盘不进 stdout，需在配置里设 `outputMode: "stdout"` 或在 Skill 中显式读取 `.playwright-cli/` 下的文件。

### 备选/补充：agent-browser（走 Skill 路线）

在以下三种情况优先用它：
1. **token 极其敏感** —— 它输出精简（操作成功仅 7 字符，对比 playwright-cli 的 70–280 字符），长流程累积差距显著。
2. **需要登录自动化** —— `auth save` 存凭据后 `auth login` 自动等待表单出现并填写，比手写登录流程省事得多。
3. **需要抓包/性能诊断** —— `route` 请求拦截、`har` 录制、`vitals` Core Web Vitals，这些 Playwright MCP 没有。
4. **内网无法查外网文档** —— 内置随版本分发的 Skill 文档，离线可读。

### 调试场景叠加：chrome-devtools-mcp

若需要在内网排查"页面为什么慢""哪个请求失败""控制台报什么错"，叠加这一个即可，它提供完整的网络请求、控制台、性能追踪（含 Lighthouse 洞察）能力，是另外两者都不覆盖的。仅 Chrome 环境的话成本很低。

### 不推荐：server-puppeteer

工具仅 7 个、仅 Chromium、**只能靠截图 + 视觉模型理解页面**。本环境视觉模型能力有限，且截图 token 成本高，性价比最低。

## 五、内网落地要点

### 1. 有网机器上预打包

```bash
# 建一个干净的打包目录
mkdir playwright-mcp-offline && cd playwright-mcp-offline
npm init -y
npm i @playwright/mcp

# 下载浏览器，并指定到可移植目录
PLAYWRIGHT_BROWSERS_PATH=./browsers npx playwright install chromium

# 整体打包带走（含 node_modules 与 browsers）
```

### 2. 内网 MCP 配置（不要用 `npx -y`，离线会拉包失败）

```json
{
  "mcpServers": {
    "playwright": {
      "command": "node",
      "args": ["D:/tools/playwright-mcp-offline/node_modules/@playwright/mcp/cli.js"],
      "env": {
        "PLAYWRIGHT_BROWSERS_PATH": "D:/tools/playwright-mcp-offline/browsers"
      }
    }
  }
}
```

### 3. 免分发浏览器（推荐优先尝试）

内网机器通常已装 Chrome 或 Edge，优先配置 `executablePath` / `channel` 直接复用，省去数百 MB 的二进制分发：

```json
{
  "mcpServers": {
    "playwright": {
      "command": "node",
      "args": [
        "D:/tools/playwright-mcp-offline/node_modules/@playwright/mcp/cli.js",
        "--executable-path", "C:/Program Files/Google/Chrome/Application/chrome.exe"
      ]
    }
  }
}
```

### 4. 登录态复用

内网系统一般需要登录，两种做法：
- **导出导入**：在已登录的浏览器里 `state-save auth.json`，内网机器 `state-load auth.json` 直接复用，避免 agent 处理登录流程。
- **接管现浏览器**：agent-browser 用 `--auto-connect` 连到已经开着并登录好的 Chrome，最省事。

### 5. 本地 HTML 页面

必须先起 HTTP 服务再访问，不要直接给 `file://` 路径：

```bash
python -m http.server 8099 --bind 127.0.0.1
```

## 六、已实测确认的坑（部署时留意）

1. **playwright-cli 封禁 `file://`** —— 实测报错 `Access to "file:" protocol is blocked`，内网处理本地 HTML 必踩。
2. **常驻进程会持有 stdout 管道** —— 两个 CLI 都会拉起守护进程/ MCP server，若用管道捕获输出会一直等不到 EOF 而挂死。自动化脚本里务必把输出重定向到文件再读回，并给子进程传 `stdin=DEVNULL`。
3. **agent-browser 首次冷启动约 2 秒** —— 后续命令约 0.7–0.9 秒/条，属于守护进程常驻后的常规开销。
4. **npm 11 默认拦截 install scripts** —— 安装时出现 `allow-scripts` 警告，agent-browser 依赖 postinstall 拉取平台二进制，内网打包时要确认这一步确实执行了。

## 七、参考架构：oh-my-pi（omp）的浏览器设计

「OMP」即 **oh-my-pi**（命令名 `omp`，官网 `omp.sh`），是 **Pi**（Mario Zechner / badlogic 的 `pi-mono`）的深度 fork，由 Can Bölük（@can1357）维护。~55k 行 Rust 核心 + TypeScript，32 个内置工具，MIT。

它与浏览器生态里其他方案的根本差别：**浏览器不是外挂的 MCP/Skill，而是原生内置在运行时里的**。

### 7.1 一句话设计

> `browser` — Puppeteer tabs over headless Chromium, CDP-attached apps, or your own Chrome via the relay.

Agent 不调一堆 `browser_*` 工具，而是在隔离的标签页运行时里**写代码操作句柄**：

```javascript
browser action:"open"  name:"wiki" url:"https://en.wikipedia.org"
browser action:"run"   name:"wiki" code:"await tab.observe(); await tab.click('text/Log in');"
browser action:"close" name:"wiki" kill:true
```

四种浏览器来源：`headless`（进程内起无头 Chromium）、`spawned`（**驱动 Electron / 桌面应用**）、`connected`（连已有 CDP 端点）、`relay`（**接管你已登录的 Chrome 标签页，且不抢焦点**）。

### 7.2 三个最值得抄的设计

1. **双视图观察** —— `observe()` 返回结构化元素清单 + 数字 id（默认只收 18 种可交互 role），`ariaSnapshot()` 返回带 `ref(eN)` 的 aria 树。一个扁平省 token，一个层级保上下文，共享同一套定位机制。走 a11y 路线，**不依赖视觉模型**。
2. **三级超时预算** —— 单元格预算留 1s headroom，交互类 8s、观察类 20s、**选择器零匹配 2s 快速失败**。拿到的永远是"点击超时"这种可诊断错误。
3. **browser-relay** —— Chrome 扩展 + 本地中继，伪装成标准 CDP 端点（`/json/version`、`/json/list`、`/cdp`），按需接管单个已登录标签页。配套 `OMP.claimTarget` 认领、标签页分组、debugger ban 自动恢复、**不抢焦点**。

外加 **Stealth 默认开启**，以及**引用计数 + 回合结束回灌提示**构成的浏览器进程防泄漏闭环。

### 7.4 对本文选型结论的影响

| 项 | 启发 |
| --- | --- |
| 双视图观察 | 印证第一节结论：本环境（GLM-5.2 + qwen3.6-VL）**必须走 a11y 树路线**，别走截图 + 视觉 |
