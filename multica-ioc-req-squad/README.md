# Multica IOC 需求小队 · 智能体与流程设计

一套可直接装配到 **Multica 自托管实例** 上的「需求分析小队」：五个通用能力单元 + 一份配置驱动的流程控制文本，把"人写需求"变成"小队协作产出需求文档"。

**适用场景**：内网环境、只有自研 agent CLI（codeagent3.0，Claude Code 套壳，内置 GLM-5.2）、无任何外部模型 API key。

---

## 设计要点（四条，先看这个）

**1. 智能体不知道流程。** 五份提示词里找不到"第一轮""被打回后""交给审核"这类编排语言。顺序、循环、回退、挂载条件全部由小队的「流程控制」字段驱动——换个队、换套流程，提示词一个字都不用改。

**2. 能力单元数 > 实际使用数。** 五个角色不是每单都跑五个。队长、写手、审核员常驻；**现状核对官与原型官是条件挂载**，不命中触发条件就整环跳过。所以角色多不等于流程长，多出来的只是"能力储备"。

**3. 事实清单的防错靠结构，不靠"写对它"。** 清单是模型读代码得出的结论，必然会有错条目。所以目标不是"永不犯错"，而是**错误进不了正文 + 进了正文也能精确定位**：前者靠置信度三档（`存疑`/`未找到` 不得进正文），后者靠文档附录的引用映射表（清单条目被推翻时，定点整改受影响章节，不必全文重审）。

**4. 两条独立计数线。** 机器审查 R1~R3 一条线（收敛阀门：第 3 轮只认阻塞级）；**人审返工**另一条线，不占三轮额度，人打回后写手按要求整改、交回直接再给人看，默认不重跑机器审查。

## 装配五步

1. 建五个智能体，把 `01` / `02` / `03` / `06` / `08` 分别填进各自的 Instructions
2. 把 `04` **整段**填进小队的「流程控制」字段
3. `05` 与 `07` 各做成一个技能，分别绑给审核员、现状核对官
4. 写手绑已有的 `req-doc` 技能；原型官绑原型技能（两条底座各一份，见 `08` 末尾）
5. 小队 leader 设为**队长**，成员为其余四个；五个智能体挂到同一个 project（project 上指定本地代码仓路径）

## 一条需求走完全程

```
issue 指派给小队 → 队长判断挂载条件
  → [条件] 现状核对官产 facts.md → 队长形式门（只查字段齐不齐）
  → 写手出 reqdoc.md → 审核员审一轮
       ├─ 不通过 → 打回写手整改（轮次 +1，最多 3 轮；第 3 轮仅阻塞级）
       └─ 三轮全过 → [条件] 原型官产出原型
  → 状态→审核中（=等人审）@人
  → 人审 ┬─ 通过 → 已定稿
         └─ 提修改要求 → 队长派写手返工（独立计数，不占三轮）→ 直接回人审
```

产物落盘（项目 `AGENTS.md` 有规定则**项目优先**，以下是兜底值）：

```
./design-facts/<issue-key>/facts.md            事实清单
./design-reqdoc/<issue-key>/reqdoc.md          需求文档
./design-prototype/<issue-key>/index.html      可点击原型
```

## 内网使用时注意

- **取代码**：`git clone` 或稀疏检出本目录即可；仓库里的中文文件名在 git 输出里会显示成八进制转义（如 `\346\226\271...`），属正常显示，文件本身没问题
- **daemon 的 GC 会删产出**：任务隔离目录闲置超过 `MULTICA_GC_TTL`（默认 24h）会被**整个删除**。所有智能体的产物必须回传 issue 或 push 到 git，只写在工作目录里等于消失
- **空闲看门狗会误杀长任务**：`MULTICA_OPENCODE_IDLE_WATCHDOG` 默认 10 分钟且**只能缩短不能延长**。所以每个提示词里都写了"每完成一个动作就输出一行进度"——任务粒度也要切小
- **改 runtime profile 参数后要重新注册 daemon**，已启动的任务仍用旧参数；升级 Multica 时先升服务端、再逐个升 daemon
- **原型官底座 B** 需要 OpenDesign daemon 在跑；底座 A 取真实系统截图**必须人工登录**，流程会在那里停一次（这是设计内的停顿，不是卡死）
