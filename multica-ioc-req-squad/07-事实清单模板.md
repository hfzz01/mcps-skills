# 事实清单模板 · 技能内容

> **用途**：绑给现状核对官（做成技能，或直接贴在核对官提示词末尾）。
> **分工**：这份文件管「**清单长什么样**」；核对官的提示词管「**怎么采**」（检索方法、置信度判定、边界）。
> **导入方式**：放进一个 git 仓（比如和 `req-doc`、审查清单放一起），用技能的 URL 导入方式导入，再绑到现状核对官。

```
# 现状事实清单 · 输出格式

产出文件必须严格按本格式组织，节不可增删，字段不可省略。

> **适用范围：本清单是一次需求专用的，不跨需求复用。** 新需求一律新采一份，
> 哪怕涉及的模块与上一单相同。基线字段的用途是**留痕与同单内复核对账**，不是复用依据。

## 一、基线（必填）

- 分支：<本次采集所依据的分支，如 develop>
- commit：<采集时该分支的 HEAD，短 hash 即可；若无法取得则写最近提交时间>
- 采集时间：<YYYY-MM-DD>
- issue：<issue 编号或标题>
- 涉及仓：<列出本次检索覆盖到的仓>

> 这一节不是为了"以后复用"，而是为了让审核员独立复核时能对到**同一份代码状态**。
> 没有它，复核时出现"清单说 A、复核说 B"就无法裁决到底谁看错了版本。

## 二、检索覆盖声明（必填）

- 已检索：<仓 / 目录 / 模块，逐项列出>
- 使用的手段：<实际用过的关键字、检索方式。要让别人能照着重放>
- 未覆盖：<明确写出没有覆盖哪些地方，以及为什么（不在本地、无权访问、与需求无关等）>

> 这一节的作用：让下游能区分"真的不存在"和"没搜到"。不写这一节，清单里任何一条
> `未找到` 都无法被信任。

## 三、事实条目（必填，每条一个独立小节）

### F-001
- 断言：<一句话，可判定真假。不要写"可能""大概"这种模糊表述>
- 证据：<文件路径:行号>，或 <接口路径>，或 <表名.字段名>
- 置信度：确定 | 存疑 | 未找到
- 影响仓：<仓名>
- 备注：<可选。存疑条目必须在这里写清"为什么不确认">

### F-002
- 断言：
- 证据：
- 置信度：
- 影响仓：
- 备注：

（依次递增编号，不跳号、不复用已删除的编号）

**编号规则**：F- 后三位数字，按产出顺序递增。
**编号一经产出即固定**，后续修订只能改内容并记入修订记录，不得改编号 —— 下游文档的引用映射靠这个编号。

## 四、抽检结论（本节由审核员追加，核对官不得填写）

（产出时留空。审核员在机器审查阶段按风险权重抽检后在此追加。）

## 五、修订记录（本节由核对官维护）

| 时间 | 条目 | 改了什么 | 为什么 | 依据 |
|---|---|---|---|---|
| | | | | |

（首次产出时留空表头。之后每次修订追加一行，不得静默修改。）

---

## 附加要求

1. **不准写正文式段落**。清单是条目化的，每条只讲一件事。
2. **不准有证据为空的条目**。没有可定位证据的断言不许进清单。
3. **不准有未经检索的条目**。凭常识或惯例写出的内容一律不许出现。
4. **不确定就降级**。拿不准是 `确定` 还是 `存疑` 时，一律写 `存疑`。
5. **`存疑` / `未找到` 的条目同样有价值**，不要因为"没查实"就不写 ——
   它们正是下游「待确认」节的来源。诚实的空白比虚假的完整有用得多。
```

## 附：字段设计的用意

| 字段 | 为什么必须有 |
|---|---|
| **基线（分支 + commit）** | 让审核员独立复核时能对到同一份代码状态，也让人事后能判断当时看的是哪个版本。**注意它的用途不是复用**——本清单不跨需求复用 |
| **检索覆盖声明** | 区分"真的没有"和"没搜到"。这是 `未找到` 条目唯一的可信度来源 |
| **证据（文件:行号级）** | 让审核员能**复核**而不是**重查**。定位不到行号，抽查就退化成重搜 |
| **置信度三档** | 决定条目能否进文档正文。`存疑`/`未找到` 只能进「待确认」节 |
| **固定编号 F-xxx** | 需求文档的「现状依据对照表」靠它做引用映射。编号变了，映射就断了 |
| **抽检结论节** | 给审核员留一个追加位置，而不是让它去改别人的条目 —— 职责边界靠文件结构保障 |
| **修订记录** | 防止静默修改导致"写手手里的清单"和"磁盘上的清单"不一致 |

## 附：和「审查清单」的区别

这两份东西名字像，作用完全不同，别混：

| | 事实清单 | 审查清单 |
|---|---|---|
| 谁产出 | 现状核对官 | 人（预先编写，固定不变） |
| 内容 | **这次**需求涉及的具体现状事实 | 所有需求都适用的检查项 |
| 数量 | 每个 issue 一份 | 全队共用一份 |
| 会不会变 | 会（有修订记录） | 基本不变（改了就是升级检查项） |
| 跨需求复用 | **不复用**，每单新采一份 | 一直复用，它本来就是所有需求通用的 |
