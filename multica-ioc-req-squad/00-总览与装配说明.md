# IOC 需求小队 · 总览与装配说明

> 本目录是当前版本：**五个智能体 + 一个小队流程**，按「通用能力单元 + 配置驱动编排」组织。
> 更早的 `multica-ioc-需求小队设计.md` 已作废（那一版假定存在四个角色，与你的实际形态不符）。

---

## 一、架构：三层，各管各的

```
┌─ 项目层（数据）────────────────────────────────┐
│ 项目仓 AGENTS.md：功能地图 / 分支规则 develop     │
│ 产物路径 / 跨仓约定 / 原型底座（可选）             │
│ project 上挂的本地代码仓路径                      │
└───────────────────────────────────────────────┘
                    ▲ 被读取（只读）
┌─ 小队层（配置：编排）──────────────────────────┐
│ 小队流程控制字段：阶段顺序 / 条件挂载 / 循环轮次 /  │
│ 回退 / 人审返工 / 状态与 label / 派单模板 /        │
│ 目录与分支规则 / 原型底座默认值                    │
└───────────────────────────────────────────────┘
                    ▲ 被读取
┌─ 智能体层（能力单元，可跨队复用）────────────────┐
│ 常驻：  队长（流程执行器）                        │
│        写手（需求文档产出，绑 req-doc）            │
│        审核员（文档审查 + 清单抽检，绑审查清单）     │
│ 条件挂：现状核对官（事实采集，绑事实清单模板）        │
│        原型官（可点击原型，绑原型技能，两条底座）     │
└───────────────────────────────────────────────┘
```

**核心原则：智能体不知道流程。** 五个提示词里都找不到"第一轮""被打回后""交给审核"这类编排语言——顺序、循环、回退、挂载条件全部由小队流程字段驱动。这样它们换个队、换套流程照样能用。

**「能力单元数 > 实际使用数」是这套设计的要点。** 五个角色不是每单都跑五个：核对官和原型官**条件挂载**，不命中就整环跳过。所以角色变多不等于流程变长。

### 目录布局（产物落盘）

```
./design-facts/<issue-key>/facts.md            事实清单
./design-reqdoc/<issue-key>/reqdoc.md          需求文档
./design-prototype/<issue-key>/index.html      可点击原型
```

规则：**三个根目录 + 一层 issue 目录 + 固定文件名**。同一时间会跑多个 issue，每个 issue 产出多个文件，所以一律以 issue 名建一层目录归类。`<issue-key>` 用 issue 编号（如 `IOC-123`），没有编号就用标题。

项目 AGENTS.md 若有自己的规定，**项目优先**，以上是兜底值。

## 三、一条需求怎么走（完整链路）

```
issue 指派给小队
      │
      ▼
 队长接单，判断挂载条件
      │
      ├─ 命中核对条件 ──→ 现状核对官 → facts.md
      │                        │
      │                    队长形式门检查（只查字段齐不齐）
      │                        ├─ 不合格 → 退回重做（不计轮次）
      │                        └─ 合格 ──┐
      │                                   │
      └─ 未命中 ──────────────────────────┤
                                          ▼
                                     写手出 reqdoc.md（含附录「现状依据对照表」）
                                          │
                                          ▼
                                     审核员审一轮 ──不通过──→ 打回写手整改（轮次+1）
                                          │                        ▲
                                          │                        └── 最多 3 轮
                                      三轮全过                        第 3 轮仍不过 → 阻塞 @人
                                          │
                                          ▼
                                   队长判断原型挂载条件 + 给出底座
                                          │
                          ┌───────────────┴───────────────┐
                          ▼                               ▼
                   命中原型条件                        未命中
             原型官（底座 A 或 B 二选一）
                          └───────────────┬───────────────┘
                                          ▼
                                状态→审核中（=等人审），@你
                                          │
                    ┌─────────────────────┴─────────────────────┐
                    ▼                                           ▼
               你确认通过                              你提出修改要求
                    │                                           │
                    ▼                                           ▼
                已定稿                              队长派写手做「人审返工」
                                                            （不占三轮额度）
                                                            写手交回 → 直接回你
                                                            （不重跑机器审查）
```

**状态语义**：`待分派` → `编写中` → `审核中`（**只表示等人审**）→ `已定稿`。
机器审查与人审返工期间状态都保持 `编写中`，只用 label（`机器审查-R1/R2/R3`、`人审返工`）标记进度。

## 四、五个关键设计点

**1. 队长被刻意压薄。** 它只做四件事：读流程、读状态、判断下一步、派单。新增的"形式门检查"也只查**字段齐不齐**，不查断言对不对——一旦让它判断内容真假，就既读代码又和审核员职责重叠，通用性就没了。

**2. 通用能力靠输入喂，不靠提示词写死。** "第三轮只准报阻塞级"这条：**规则**在审核员提示词里，**参数**（哪一轮是最终轮）由小队流程决定、派单时传入。产物路径、分支基准、抽检比例、**原型底座**同理。

**3. 派单说明是唯一的上下文载体，五种模板。** 智能体互不感知、不对话，全靠这条评论传递上下文。字段省一个，下游就得猜，猜就是幻觉。

**4. 事实清单的防错靠结构，不靠"写对它"。** 清单是模型读代码的结论，必然会有错条目。所以设计了：
   - **置信度三档** —— `存疑`/`未找到` 进不了正文，只进「待确认」节（错误进不了文档）
   - **引用映射** —— 清单条目被推翻时，靠附录定位受影响章节，定点整改（错误的影响面可控）
   - **独立抽检** —— 审核员拿代码去撞清单，高风险四类全查（错误能被发现）

**5. 计数有两条线，别混。** 机器审查 R1~R3 是一条线（收敛阀门：第三轮锁阻塞级）；人审返工是另一条线，次数独立计数，不占三轮额度。混在一起的后果是：人改一句话也要重跑三轮，或者返工把轮次撑爆、误触发轮次超限。

## 五、五处我做了主张，你可以推翻

**① 事实清单独立成技能**（`07`）。你说"没清单，直接写在审核员里"——为了跨队复用我拆开了。嫌多一个技能要维护的话，直接把内容贴到核对官提示词末尾也能跑，代价是失去复用性。

**② 审查清单独立成技能**（`05`）。同理。另外我在里面新增了 **K 节「事实清单的使用纪律」**——这是有清单之后才需要的新检查项，专门查"文档有没有滥用或伪造清单依据"。

**③ 机器审查阶段用 label 承载轮次。** 状态保持你原本的语义（`审核中` 永远只等于"等人审"）。不想加 label 就删掉，队长会退化成只读评论数轮次。

**④ 队长做「形式门检查」。** 这是新增的一环，目的是把残缺清单挡在写手之前。它不读代码，只查字段。如果你觉得队长不该碰清单文件，可以改成让核对官在清单里自带一个"自检节"，队长只检查该节是否存在。

**⑤ 抽检比例定在 50%（高风险四类 100%）。** 你说 token 不是约束，我比原计划的 30% 调高了。想更严可以改成全量。

## 六、还没定的小事（都不卡跑通）

1. **人审通过后谁把状态改成 `已定稿`** —— 队长自动改，还是你手动改？
2. **原型技能要精简两版**。`prototype-studio/SKILL.md` 现在是给"人 + AI 对话"写的，绑给智能体需要把"停下来问用户"改成"在 issue 里留评论等待"。OpenDesign 那一侧则要写一份"怎么用 MCP 拿设计系统与模板"的技能说明。这两份我可以顺手做，说一声就行。
3. **要不要给底座 B 做一份 `DESIGN.md`**。把你们 Element 风格的主色、间距、组件用法写进去（`prototype-studio` 的 `themeCss` 指向的 `element-ui/lib/theme-chalk/index.css` 是现成素材）。做完之后两个底座的产出风格就统一了，一次性投入。不做也能跑，代价是底座 B 的产出跟你们系统不像。
