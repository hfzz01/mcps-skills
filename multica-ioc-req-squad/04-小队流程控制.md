# 需求小队 · 流程定义

## 一、角色与能力

五个能力单元，互不感知、互不对话。所有交接经队长，以派单说明评论留痕。

**常驻（每单必经）**
- 队长：流程执行器。读本流程 + 读 issue 状态 → 判断下一步 → 派单。不产出内容、不读代码
- 写手：需求文档产出。绑 req-doc 技能。只读代码
- 审核员：需求文档审查 + 事实清单抽检。绑审查清单技能。只读代码，只输出结论

**条件挂载（命中条件才激活，不命中则整环跳过）**
- 现状核对官：现状事实采集。绑事实清单模板技能。只读代码，只产出清单，不产出需求
- 原型官：可点击原型产出。绑原型技能。基于已定稿的需求文档生成。
  按「原型底座」参数走两条不同路径（见第三节），其中底座 A 需要人工登录真实系统

## 二、阶段清单

| 阶段 | 执行者 | 进入条件 | 完成后 |
|---|---|---|---|
| 接单分派 | 队长 | issue 已指派给本小队 | 判断挂载条件，派下一环 |
| 现状核对 | 现状核对官 | 命中核对挂载条件 | 产出 facts.md，交回队长 |
| 形式门检查 | 队长 | 核对官交回 | 合格→派写手；不合格→退回核对官 |
| 文档编写 | 写手 | 收到派单说明 | 产出 reqdoc.md，交回队长 |
| 机器审查 | 审核员 | 收到派单说明 | 输出【审-N】结论 |
| 原型产出 | 原型官 | 三轮审查全过 且 命中原型挂载条件 | 产出原型，交回队长 |
| 待人工审核 | 人类 | 三轮通过（若挂原型则等原型产出后） | 人类判定 |
| 人审返工 | 写手 | 人类在「审核中」状态提出修改要求 | 产出整改版，交回队长 |
| 定稿 | — | 人类确认通过 | 状态→已定稿 |
| 阻塞 | — | 命中异常分支 | 等人类介入 |

## 三、挂载条件（队长判断，命中任一即挂载）

**现状核对官（命中任一）**
1. 需求涉及 2 个以上子仓
2. 涉及库表变更（新增或修改表、字段）
3. 涉及接口契约变更（新增接口、改入参或返回体）
4. 涉及新页面

**原型官（命中任一）**
1. 涉及新页面
2. 涉及现有页面的交互或布局变更
3. 需求方明确要求原型

**原型底座（命中原型官时，队长必须在派单里给出取值）**

| 底座 | 用什么 | 适合 | 代价 |
|---|---|---|---|
| `A-prototype-studio` | 截真实系统 + 热区跳转 | 以**改造现有页面**为主的需求 | **必须人工登录**，流程会停一次 |
| `B-opendesign` | OpenDesign（MCP 供料 + 生成） | 以**新页面 / 新交互**为主的需求 | 全自动，但风格不一定像现有系统 |

取值优先级见第九节。默认值取 `B-opendesign`，因为它不阻塞流程。

**不命中的处理（这一条很重要，别省）**
- 未挂核对官 → 写手自行核实现状（退回原行为），其「现状依据对照表」直接填代码证据，不经清单
- 未挂原型官 → 三轮通过后直接进入待人工审核

## 四、流转规则

1. issue 新建并指派给本小队 → 队长判断挂载条件
   - 1a. 命中核对条件 → 派现状核对官，状态→编写中
   - 1b. 未命中 → 直接派写手（轮次 1/3，策略=全量输出），状态→编写中
2. 核对官产出 facts.md → 队长执行**形式门检查**（不读代码，只查形式）：
   - 每条是否含：id / 断言 / 证据 / 置信度
   - 是否含「检索覆盖声明」
   - 是否含「基线」（分支 + commit）
   - 合格 → 派写手（轮次 1/3，策略=全量输出）
   - 不合格 → 退回核对官重做，附明缺什么。**此环不计轮次**，且不得派写手
3. 写手产出 reqdoc.md → 队长派审核员，轮次 1/3，策略=全量输出，label→机器审查-R1
4. 审核员结论为**通过**（阻塞 0）→ 转第 7 步
5. 审核员结论为**不通过** → 队长派写手整改
   输入 = 待审文档 + 本轮审查结论 + 本轮被推翻的清单条目及其影响章节
   状态→编写中，轮次 +1
6. 第 2 轮策略=全量输出，label→机器审查-R2；第 3 轮策略=**仅阻塞级**，label→机器审查-R3
   —— 第三轮只认阻塞级，建议级不计入结论。这是三轮循环能收敛的关键
   第 3 轮仍为不通过 → 命中异常分支，见第七节
7. 三轮全过 → 队长判断原型挂载条件：
   - 7a. 命中 → 派原型官（输入 = 定稿文档 + 事实清单 + 原型底座参数）
   - 7b. 未命中 → 状态→审核中，@人类负责人
8. 原型官产出后 → 状态→审核中，@人类负责人，附原型路径
   （底座 A 会中途停一次等人工登录，见第七节第 5 条）
9. 人类确认通过 → 状态→已定稿

**—— 以下是人审返工循环，独立于机器审查三轮 ——**

10. 人类在 `审核中` 状态提出修改要求（评论里 @队长 或直接说明要改什么）→ 队长派写手返工
    - 状态→编写中，label→`人审返工`
    - 输入 = 当前文档 + **人类反馈原文**（队长原文转述，不得加工、不得转译成自己的理解）
    - 此循环**不占用机器审查的 3 轮额度**，它与 R1~R3 是两条独立计数线
    - 整改规则与机器审查轮相同：**只改被点名的部分**，额外改动必须显式声明
11. 写手交回 → 队长**不再派机器审查**，直接状态→审核中，@人类，附整改说明
    - 理由：人已经是最高裁量，机器再拦一轮只增加等待，不增加信息
    - 例外：人类明确要求"再过一遍机器审核"时，派审核员跑 1 轮（策略=仅阻塞级），
      该轮也**不计入** R1~R3
12. 返工改动了与页面/交互相关的部分 → 队长重新判断原型挂载条件，命中则派原型官重做原型
    - 判断依据：写手交接评论里的「是否影响原型范围」字段（队长不读文档，只读这一行）

轮次上限：**3**（仅指机器审查）。以审核员输出的 `【审-N】` 为准，取最大的 N（不靠模型记忆）。

## 五、事实清单的三条纪律

清单由核对官产出、落盘于产物路径。**清单是单次需求专用的，不跨需求复用。**

**纪律 1 —— 置信度决定可用性**
- `确定` → 可作为文档正文的论据
- `存疑` / `未找到` → **写手不得写进正文**，只能写进文档的「待确认」节
- 这一条是防"在错误基础上写作"的第一道闸：把清单里不确定的部分隔离在正文之外

**纪律 2 —— 引用映射**
写手在需求文档附录维护「现状依据对照表」，格式：`文档第 X 节 ← F-012`。
作用：清单条目被推翻时，据此**精确定位文档受影响章节**，做定点整改，而不是全文重审。

**纪律 3 —— 基线留痕，不做复用**
清单头部必须记录基线（分支 + commit）。用途有两个：
- 让审核员独立复核时能对到**同一份代码状态**（否则"清单说 A、我说 B"无法裁决）
- 让人类事后能判断这份清单当时看的是哪个版本

**不跨需求复用**：新需求一律新采一份清单，哪怕模块相同。不设"复用旧清单"动作，
因此也不需要时效比对规则——那是复用才需要的机制，这里不存在。

## 六、状态与 label

**状态（看板流转用）**
- `待分派` —— 新建，等队长处理
- `编写中` —— 核对官采集、写手编写、机器审查、写手整改、**人审返工**期间
- `审核中` —— **正在等人审**
  （进入条件：三轮机器审查全过；若挂原型则等原型产出后。此状态只表示等人，不表示机器在审）
- `已定稿` —— 人审通过

**label（过程可见性用）**
- `机器审查-R1` / `-R2` / `-R3` —— 当前处在第几轮机器审查
- `人审返工` —— 人审阶段打回，写手正在按人类反馈整改（不占用三轮额度）
- `清单有误` —— 审核员抽检推翻了清单条目
- `阻塞` —— 命中异常分支，等人类
- `需业务确认` —— 缺必需输入，等人类

> 机器审查与人审返工期间都不改变状态（保持 `编写中`），只挂 label ——
> 这样看板上"审核中"永远只等于"等人审"。

## 七、异常分支

1. **轮次超限**：第 3 轮仍有阻塞级 → label `阻塞`，@人类负责人，
   附：卡在第几轮、卡在哪几条、每条原文
2. **缺必需输入**：需求原话为空、产物路径无法确定等 → label `需业务确认`，@人类说明缺什么
3. **状态与流程对不上**：队长判断不出下一步 → 不许猜，label `阻塞`，@人类说明冲突点
4. **核对官形式门连续 2 次不合格** → label `阻塞`，@人类（说明它缺什么字段，可能提示词需调整）
5. **原型官需要人工登录**（**仅当底座 = A-prototype-studio**）：
   原型官会主动在 issue 中提示并等待，队长此时**不得判定为卡死**，保持 `编写中` 直到原型官交回
6. **人审返工次数过多**：同一 issue 累计 3 次人审返工仍未通过 → label `阻塞`，@人类。
   这不是流程故障，多半是需求本身没谈拢，需要人来定而不是继续让写手改
7. **原型官底座不可用**（A 无浏览器可连 / B 的 OpenDesign daemon 未启动）：
   原型官会在评论中报明。队长**不自行换底座**，标 `需业务确认` @人类，由人决定换底座还是跳过原型

## 九、取值优先级（项目优先，队伍兜底）

**产物路径**：先取 project 的 AGENTS.md 规定 → 项目没有规定则用下面的兜底值。

兜底值规则：**三个根目录 + 一层 issue 目录 + 固定文件名**。
（同一时间会跑多个 issue，每个 issue 可能产出多个文件，所以一律以 issue 名建一层目录归类。）

- 事实清单：`./design-facts/<issue-key>/facts.md`
- 需求文档：`./design-reqdoc/<issue-key>/reqdoc.md`
- 原型：`./design-prototype/<issue-key>/index.html`
- `<issue-key>` = issue 编号（如 `IOC-123`）；若无编号，用 issue 标题（空格与特殊字符替换为 `-`）

**分支基准**：先取 project 的 AGENTS.md 规定 → 无则用兜底值 `develop`
（注：各子仓分支可能不同，同步情况由人类预先确认；需求分析阶段统一以 develop 为核对基准）

**原型底座**：先取 project 的 AGENTS.md 规定 → 无则取本流程第三节的默认值 `B-opendesign`。
队长可按需求特征覆盖一次，但必须在派单说明里写明底座取值，不得留空让原型官自己选。

**轮次策略**：只能从本流程第四节查，队长不得自行发明

## 十、边界

- 需求分析阶段**只读不改**：任何智能体都不得 commit、push、切分支、修改业务代码
- 智能体之间不直接对话。所有交接必须经过队长，并以派单说明评论留痕
- 需求文档的修改权只属于写手；审核员只看不改；队长不碰任何文件
- **事实清单的条目内容只由核对官产出与修订**。审核员抽检发现错误时，只能在自己的「抽检结论」节里追加反证，不得改动原有条目
- 原型官不得修改需求文档。发现原型与文档不一致时，以文档为准，并在评论中报出不一致点
- **人审反馈的原文不得被队长加工**。队长转述时逐字照抄；改写人类的意思，等于伪造需求来源

## 附：这份流程定义里的五个关键机制

**1. 「条件挂载」是这套设计能长到五个角色的原因。** 核对官和原型官不进主链路——不命中条件就整环跳过。所以角色变多不等于流程变长，多出来的只是"能力储备"，不是"每单都要走的路"。

**2. 「形式门检查」由队长做，是零成本拦截。** 队长不读代码，只查清单字段是否齐全（id / 断言 / 证据 / 置信度 / 覆盖声明 / 基线）。残缺清单连写手都碰不到，从源头掐断"在残缺事实上写需求"。

**3. 「引用映射」是清单出错的止损阀。** 有了它，清单条目被推翻时可以精确算出文档哪几节受影响，做定点整改。没有它，清单错一条只能全文重审，三轮审查全部白跑。

**4. 「置信度三档」把不确定性隔离在正文之外。** 这是防错的第一道闸——`存疑` / `未找到` 的条目进不了正文，只能进「待确认」节。用户看到的每一句现状描述，背后都有 `确定` 级证据。

**5. 「人审返工」是独立计数线，不是第四轮。** 它不占用 R1~R3，也不改 `审核中` 的语义。这样设计有两个好处：机器审查的收敛阀门（三轮锁阻塞级）不被人为拉长；而人审发现的问题又能立刻回炉——人不需要为了改一句话而"重新走一遍三轮"。

**一句话总结防错逻辑：** 不追求清单永不犯错（办不到），追求"错误进不了正文 + 进了正文也能精确定位"。前者靠置信度，后者靠引用映射。
