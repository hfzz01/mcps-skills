# 需求小队 · 流程定义

## 〇、平台机制约束（先读这一节，它决定流程跑不跑得起来）

1. **派活靠 @提及，绝不改负责人。** 本 issue 的负责人**永远是本小队**。派活 = 发一条评论，
   把 Squad Roster 里那条完整 mention markdown 原样贴上去 @ 目标成员。
   - 普通 "@名字" 不触发任何人。
   - 改负责人 = 把持有权从小队拿走 ⇒ 之后评论不再唤醒队长、队长连改状态的权限都没有，
     链路当场断掉。
2. **成员交回 = 发一条不带任何 @ 的顶层评论。** 平台会按 issue 负责人把它回落到小队，
   自动唤醒队长。成员一旦 @ 了别的目标（**包括 @ 队长**），这个回落就被关掉。
3. **需要人类介入时 @人类负责人**（交人审、报缺、卡死）。靠显式 @ 把路由指向人，而不是队长。
4. **每个成员一次只发一条评论**。中途要留痕就用 `/note` 开头——以 `/note` 开头的评论
   不触发任何智能体。普通评论（哪怕不带 @）会被回落到队长，让它白跑一轮评估。
5. **队长每轮必须记录**：
   `multica squad activity <issue-id> <action|no_action|failed> --reason "<简短原因>"`
   outcome 取 `action` / `no_action` / `failed`。**不需要动作时静默退出、不发任何评论。**
6. **状态只用平台内置值**：`todo` / `in_progress` / `in_review` / `done` / `blocked`。
   不使用自定义状态 —— 自定义状态只继承四类生命周期语义，不继承平台的失败回滚等具体行为。
7. **阶段与轮次写进 label，队长读 label 判定进度**，不解析评论历史。
   评论里混着系统记录、成员进展与历史派单，靠文本解析迟早出错；label 是结构化字段，干净可靠。
8. **人类要唤醒队长，必须在评论里显式 @队长 或 @小队。**
   用 `/note` 或 `@all` 发的评论不会触发任何智能体。

## 一、角色与能力

五个能力单元，互不感知、互不对话。所有交接经队长，以派单说明评论留痕。

**常驻（每单必经）**
- 队长（= 本小队 leader）：流程执行器。读本流程 + 读 issue → 判断下一步 → 派活。
  不产出内容、不读代码、**不改负责人**
- 写手：需求文档产出。绑 req-doc 技能。只读代码
- 审核员：需求文档审查 + 事实清单抽检。绑审查清单技能。只读代码，只输出结论

**条件挂载（命中条件才激活，不命中则整环跳过）**
- 现状核对官：现状事实采集。绑事实清单模板技能。只读代码，只产出清单，不产出需求
- 原型官：可点击原型产出。绑原型技能。基于已定稿的需求文档生成。
  按「原型底座」参数走两条不同路径（见第三节），其中底座 A 需要人工登录真实系统

**所有成员的共同纪律**
- **绝不修改 issue 的负责人，也绝不改 issue 状态**。这两样只由队长管
- 做完后发一条**不带任何 @** 的顶层评论交回；需要人介入时 **@人类负责人**
- 绝不 @ 其他智能体

## 二、阶段清单

| 阶段 | 执行者 | 进入条件 | 期间的 label | 完成后 |
|---|---|---|---|---|
| 接单分派 | 队长 | issue 已分配给本小队 | （无） | 判断挂载条件，派下一环 |
| 现状核对 | 现状核对官 | 命中核对挂载条件 | `阶段-核对` | 产出 facts.md，交回队长 |
| 形式门检查 | 队长 | 核对官交回 | `阶段-核对` | 合格→派写手；不合格→退回核对官 |
| 文档编写 | 写手 | 收到派单说明 | `阶段-编写` | 产出 reqdoc.md，交回队长 |
| 机器审查 | 审核员 | 收到派单说明 | `阶段-审R1` / `R2` / `R3` | 输出【审-N】结论 |
| 原型产出 | 原型官 | 三轮审查全过 且 命中原型挂载条件 | `阶段-原型` | 产出原型，交回队长 |
| 待人工审核 | 人类 | 三轮通过（若挂原型则等原型产出后） | （保留上一阶段 label） | 人类判定 |
| 人审返工 | 写手 | 人类在 `in_review` 状态提出修改要求 | `阶段-人审返工` | 产出整改版，交回队长 |
| 定稿 | — | 人类确认通过 | （label 清空或保留） | 状态→`done` |
| 阻塞 | — | 命中异常分支 | `阻塞` / `需业务确认` | 等人类介入 |

> 队长**只读 label 判定当前阶段**。label 没有阶段值时 = 首次接单。
> 同一时刻只应存在一个 `阶段-*` label。

## 三、挂载条件（队长判断，命中任一即挂载）

**现状核对官（命中任一）**
1. 需求涉及 2 个以上子仓
2. 涉及库表变更（新增或修改表、字段）
3. 涉及接口契约变更（新增接口、改入参或返回体）
4. 涉及新页面

**原型官（命中任一）**
1. 涉及新页面
2. 涉及现有页面的交互或布局变更
3. 需求方明确要求原型

**原型底座（命中原型官时，队长必须在派单里给出取值）**

| 底座 | 用什么 | 适合 | 代价 |
|---|---|---|---|
| `A-prototype-studio` | 截真实系统 + 热区跳转 | 以**改造现有页面**为主的需求 | **必须人工登录**，流程会停一次 |
| `B-opendesign` | OpenDesign（MCP 供料 + 生成） | 以**新页面 / 新交互**为主的需求 | 全自动，但风格不一定像现有系统 |

取值优先级见第九节。默认值取 `B-opendesign`，因为它不阻塞流程。

**不命中的处理（这一条很重要，别省）**
- 未挂核对官 → 写手自行核实现状（退回原行为），其「现状依据对照表」直接填代码证据，不经清单
- 未挂原型官 → 三轮通过后直接进入待人工审核

## 四、流转规则

1. issue 新建并分配给本小队 → 队长把状态 `todo`→`in_progress`，判断挂载条件
   - 1a. 命中核对条件 → 派现状核对官，label→`阶段-核对`
   - 1b. 未命中 → 直接派写手（轮次 1/3，策略=全量输出），label→`阶段-编写`
2. 核对官产出 facts.md → 队长执行**形式门检查**（不读代码，只查形式）：
   - 每条是否含：id / 断言 / 证据 / 置信度
   - 是否含「检索覆盖声明」
   - 是否含「基线」（分支 + commit）
   - 合格 → 派写手（轮次 1/3，策略=全量输出），label→`阶段-编写`
   - 不合格 → 退回核对官重做，附明缺什么。**此环不计轮次**，且不得派写手
3. 写手产出 reqdoc.md → 队长派审核员，轮次 1/3，策略=全量输出，label→`阶段-审R1`
4. 审核员结论为**通过**（阻塞 0）→ 转第 7 步
5. 审核员结论为**不通过** → 队长派写手整改，label→`阶段-编写`
   输入 = 待审文档 + 本轮审查结论 + 本轮被推翻的清单条目及其影响章节
   轮次 +1
6. 第 2 轮策略=全量输出，label→`阶段-审R2`；第 3 轮策略=**仅阻塞级**，label→`阶段-审R3`
   —— 第三轮只认阻塞级，建议级不计入结论。这是三轮循环能收敛的关键
   第 3 轮仍为不通过 → 命中异常分支，见第七节
7. 三轮全过 → 队长判断原型挂载条件：
   - 7a. 命中 → 派原型官（输入 = 定稿文档 + 事实清单 + 原型底座参数），label→`阶段-原型`
   - 7b. 未命中 → 状态→`in_review`，**@人类负责人**（显式 @，不是等他看）
8. 原型官产出后 → 状态→`in_review`，**@人类负责人**，附原型路径
   （底座 A 会中途 @人类等人工登录，那一轮不会唤醒队长，见第七节第 5 条）
9. 人类确认通过（在评论里 @队长 说明通过）→ 状态→`done`

**—— 以下是人审返工循环，独立于机器审查三轮 ——**

10. 人类在 `in_review` 状态提出修改要求（评论里 @队长 或 @小队）→ 队长派写手返工
    - label→`阶段-人审返工`（状态保持 `in_review` 不变）
    - 输入 = 当前文档 + **人类反馈原文**（队长原文转述，不得加工、不得转译成自己的理解）
    - 此循环**不占用机器审查的 3 轮额度**，它与 R1~R3 是两条独立计数线
    - 整改规则与机器审查轮相同：**只改被点名的部分**，额外改动必须显式声明
11. 写手交回 → 队长**不再派机器审查**，直接 **@人类负责人**，附整改说明
    - 状态保持 `in_review`（依然在等人审）
    - 理由：人已经是最高裁量，机器再拦一轮只增加等待，不增加信息
    - 例外：人类明确要求"再过一遍机器审核"时，派审核员跑 1 轮（策略=仅阻塞级），
      该轮也**不计入** R1~R3
12. 返工改动了与页面/交互相关的部分 → 队长重新判断原型挂载条件，命中则派原型官重做原型，label→`阶段-原型`
    - 判断依据：写手交接评论里的「是否影响原型范围」字段（队长不读文档，只读这一行）

轮次上限：**3**（仅指机器审查）。以 label `阶段-审RN` 为准；若 label 缺失，退化为读审核员输出的
`【审-N】` 取最大的 N。**不靠模型记忆。**

## 五、事实清单的三条纪律

清单由核对官产出、落盘于产物路径。**清单是单次需求专用的，不跨需求复用。**

**纪律 1 —— 置信度决定可用性**
- `确定` → 可作为文档正文的论据
- `存疑` / `未找到` → **写手不得写进正文**，只能写进文档的「待确认」节
- 这一条是防"在错误基础上写作"的第一道闸：把清单里不确定的部分隔离在正文之外

**纪律 2 —— 引用映射**
写手在需求文档附录维护「现状依据对照表」，格式：`文档第 X 节 ← F-012`。
作用：清单条目被推翻时，据此**精确定位文档受影响章节**，做定点整改，而不是全文重审。

**纪律 3 —— 基线留痕，不做复用**
清单头部必须记录基线（分支 + commit）。用途有两个：
- 让审核员独立复核时能对到**同一份代码状态**（否则"清单说 A、我说 B"无法裁决）
- 让人类事后能判断这份清单当时看的是哪个版本

**不跨需求复用**：新需求一律新采一份清单，哪怕模块相同。不设"复用旧清单"动作，
因此也不需要时效比对规则——那是复用才需要的机制，这里不存在。

## 六、状态与 label

**状态 —— 只用平台内置值，不自造**

| 状态 | 含义 | 谁改 |
|---|---|---|
| `todo` | 已立项，还没开始 | 系统 / 人类建单时 |
| `in_progress` | 核对、编写、机器审查、整改、人审返工、原型 —— 全在这一档 | 队长 |
| `in_review` | **有成果在等人审**（三轮全过 / 原型产出后 / 人审返工交回后） | 队长 |
| `done` | 人审通过，定稿 | 队长（人类说通过后） |
| `blocked` | 命中异常分支，等人介入 | 队长 |

> 机器审查与人审返工期间状态都是 `in_progress` / `in_review`，**进度靠 label 表达** ——
> 这样看板上"待人工审核"永远只等于"真的在等人"。

> ⚠️ 系统行为：run 失败且该 issue 没有其他运行时，系统会把 `in_progress` **回滚成 `todo`**。
> 所以看到 `todo` 但**已有阶段 label**，那是失败回退、不是新单 —— 按 label 继续。

**label（阶段与过程可见性）**

| label | 用在什么时候 |
|---|---|
| `阶段-核对` | 现状核对官正在采集（含形式门检查） |
| `阶段-编写` | 写手正在写初稿或整改 |
| `阶段-审R1` / `阶段-审R2` / `阶段-审R3` | 处在第几轮机器审查 |
| `阶段-原型` | 原型官正在产出原型 |
| `阶段-人审返工` | 人审打回，写手正在按人类反馈整改（不占三轮额度） |
| `清单有误` | 审核员抽检推翻了清单条目 |
| `阻塞` | 命中异常分支，等人类 |
| `需业务确认` | 缺必需输入，等人类 |

> **同一时刻只应存在一个 `阶段-*` label。** 队长换阶段时先摘旧的再挂新的。
> 阶段 label 是队长判定进度的唯一依据，所以它比状态更重要。

## 七、异常分支

1. **轮次超限**：第 3 轮仍有阻塞级 → 状态→`blocked`、label `阻塞`、**@人类负责人**，
   附：卡在第几轮、卡在哪几条、每条原文
2. **缺必需输入**：需求原话为空、产物路径无法确定等 → `blocked` + label `需业务确认` + @人类，说明缺什么
3. **状态与流程对不上**：队长判断不出下一步 → 不许猜，`blocked` + @人类说明冲突点
4. **核对官形式门连续 2 次不合格** → `blocked` + @人类（说明它缺什么字段，可能提示词需调整）
5. **原型官需要人工登录**（**仅当底座 = A-prototype-studio**）：
   原型官会**@人类负责人**并在 issue 中等待。这一轮**不会唤醒队长**，所以队长不需要任何特判。
   人登录完回复原型官，原型官会被唤醒继续
6. **人审返工次数过多**：同一 issue 累计 3 次人审返工仍未通过 → `blocked` + @人类。
   这不是流程故障，多半是需求本身没谈拢，需要人来定而不是继续让写手改
7. **原型官底座不可用**（A 无浏览器可连 / B 的 OpenDesign daemon 未启动）：
   原型官会 @人类并报明。队长**不自行换底座**，若被唤醒则 `blocked` + label `需业务确认` + @人类

| 项 | 上一版 | 这一版 | 为什么 |
|---|---|---|---|
| **派活方式** | 队长"把 issue 指派给目标智能体" | **用 Squad Roster 的提及链接 @ 目标成员，绝不改负责人** | 平台机制：改负责人会让小队失去持有权，评论不再唤醒队长、状态权限也没了。**这是内网实测翻车的头号原因** |
| **成员交回** | 只写"交回队长"，没定义动作 | **发一条不带任何 @ 的顶层评论** | 平台的回落规则：显式 @ 了别的目标就不再回落。没定义动作 ⇒ 链路静默停住 |

| **阶段与轮次** | 靠解析评论里的 `【派单】` / `【审-N】` | **靠 label**（`阶段-核对/编写/审R1~R3/原型/人审返工`） | 队长跨 run 无记忆，只能靠 issue 现状重建进度；评论流噪声大，label 是结构化字段 |
