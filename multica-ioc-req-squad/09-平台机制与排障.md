## 一、派活与唤醒：整个流程的命门

### 1.1 谁触发谁

| 动作 | 结果 |
|---|---|
| 把 issue 分配给**小队** | 负责人 = 小队（`assignee_type=squad`）。系统**只给 leader 入队一次**，不是给每个成员都入队 |
| leader 在评论里 **@提及 某个成员** | 被 @ 的成员入队运行。**不改负责人、不改状态** |
| 成员发一条**不带任何 @** 的评论 | 平台按 issue 的负责人回落到**小队** ⇒ **自动唤醒 leader** |
| 成员发一条**显式 @了别人**的评论 | **不再回落**（显式 @ 被当作路由信号）⇒ leader 不会被唤醒 |
| 成员发一条 `/note` 开头的评论 | **不触发任何智能体**（适合贴中途进展、纯留痕） |
| leader 改 issue 负责人 | ❌ 灾难。小队失去持有权 ⇒ 之后评论不再唤醒 leader，leader 也失去改状态的权限 |
| 人类发 `/note` 或 `@all` | 不触发任何智能体（`@all` 只通知人，不含 agent） |

> **一句话：不带 @ 回队长，带 @ 回别人，`/note` 谁也不惊动。** 这三条是整个流程能跑起来的地基。

### 1.2 leader 每轮被系统注入的东西（不可编辑）

leader 每次运行时，系统会往它的指令后面追加三段（顺序固定）：

1. **Squad Operating Protocol** —— 硬编码，不可编辑。关键条款：
   - 你是 leader，**只协调、不干活**。哪怕任务看起来是"你来改这个 bug"，也必须 @提及 派给成员
   - **派活必须用完整的 mention markdown** `[@Name](mention://<type>/<UUID>)`。**普通 "@名字" 不触发任何人**
   - 派活评论**必须简短**：不许复述 issue 正文（成员自己有上下文）。两三句就够
   - **每轮必须** `multica squad activity <issue-id> <action|no_action|failed> --reason "..."`
   - **派完就停**：不继续工作、不写代码、不开文件
   - **不需要动作时静默退出、不发任何评论**（连"我决定不动作"也不许发）
   - 状态责任分两种：
     - issue 属于本小队 → **首轮把父任务推到 `in_progress`**；成员干活期间保持；**确认整体目标达成才推 `in_review`**；`done` 留给人类
     - issue 不属于本小队（被 @ 拉进来）→ **禁止改该 issue 的状态**
   - Hard rule：**子任务与 @提及 二选一**。`--status todo` 的子任务 + agent assignee **指派即触发**；若同时在父 issue 上又 @ 同一个 agent，它会**并行跑两次**
2. **Squad Roster** —— leader 自己的行 + 每个未归档成员一行，每行带**完整的 mention markdown**；agent 成员还会列出它绑定的 skills（供 leader 按能力派活）
3. **Squad Instructions** —— 就是你在小队里填的「流程控制」字段（对应我们的 `04`）。**只给 leader 看**，不注入成员

> ⚠️ 因为成员看不到 Squad Instructions，**成员需要的规则必须写在成员自己的提示词里**。

### 1.3 评论合并（coalescing）

- 同一 agent 已有**等待中**的运行 ⇒ 新评论**合并**进那个运行
- 同一 agent **正在跑** ⇒ 后续评论等本轮结束后**合并成一次**后续运行
- 一条评论 @ 了多个不同 agent ⇒ 各自一个运行；@ 同一个 agent 多次 ⇒ 只留一个

> 所以：**一个回合只发一条评论**。分三条发，时序会被合并打乱。

## 二、状态模型

内置 7 状态 / 4 分类：

| 分类 | 内置状态 | 含义 |
|---|---|---|
| `unstarted` | `backlog` / `todo` | 未开始（计划中 / 已排期待启动） |
| `started` | `in_progress` / `in_review` / `blocked` | 进行中 / 等审查 / 暂时推进不了 |
| `done` | `done` | 成功完成，终态 |
| `closed` | `cancelled` | 不再追，终态 |

**关键行为**：

- 分配给 agent 或小队时**立即入队**，**除非** issue 在 `backlog`（`backlog` 是停车场，不启动运行）
- 智能体按工作进展自己写状态：开始干活 → `in_progress`；**交付 → `in_review`**；跨轮继续 → 保持 `in_progress`；只答疑 → 不动状态
- `done` 通常由人类确认，或由 PR 合并触发
- **两个系统行为**（不由 agent 写）：
  - run 失败 + 该 issue 没有其他运行 + 没有待重试 ⇒ `in_progress` **回滚成 `todo`**
  - 关联的 GitHub PR 合并（close intent）且无其他开放 PR ⇒ 变 `done`

**自定义状态的坑**：

> 自定义状态**只继承四类生命周期语义**，**不继承** 内置 Backlog 的停泊、In Review 的完成、Blocked 的失败、In Progress 的失败恢复。
> 需要那些行为时，必须用固定内置状态。

所以本设计**直接用内置值**，不自造。我们的 `待分派/编写中/审核中/已定稿` 与 `todo/in_progress/in_review/done` 恰好一一对应。

## 三、运行（run）中断与失败 —— 排障手册

### 3.1 先跑这四条命令

```bash
multica version
multica daemon status --output json
multica daemon logs --lines 100
multica issue runs <issue-id>          # 看这条 issue 的每个 run 与它的失败原因码
```

界面上也能看：issue 右侧栏的 **Execution log**（默认展开，活跃运行钉在顶部，历史在 "Show past runs" 后面）。

### 3.2 运行状态机

`deferred` → `queued` → `dispatched` → （`waiting_local_directory`）→ `running` → `completed` / `failed` / `cancelled`

| 状态 | 超时规则 |
|---|---|
| `queued` | 等 runtime 认领。只要 runtime 还在心跳就一直排；**排队本身不会过期**。仅当「runtime 失联超过重连宽限期」**且**「run 也排了那么久」两条同时成立才失败 |
| `dispatched` | **超过 5 分钟**没进 running ⇒ 判失败 |
| `waiting_local_directory` | 自己没有超时，等目录锁释放 |
| `running` | **没有固定时长上限**。活跃度看 runtime 心跳（每 15 秒一次）；心跳丢失后约 3 分钟内标记离线，其 run 一并失败 |

### 3.3 失败原因码对照表

**平台侧（无前缀）**

| 原因码 | 含义 | 怎么办 |
|---|---|---|
| `runtime_offline` | 运行期间 runtime 掉线 | 恢复 runtime 后重试 |
| `queued_expired` | runtime 失联超宽限期且 run 也排了那么久 | 确认 runtime 在线后重试 |
| `runtime_recovery` | daemon 重启后回收了被打断的 run | 直接重试 |
| `environment_prepare_failed` | daemon 没能准备好执行环境（工作目录或写进目录的本地配置） | 看原始错误，查该机器的磁盘/权限/目录占用/CLI 本地配置 |
| `cancelled` | 被手动停止，或随归档/删除一起取消 | 无需处理 |
| `timeout` | 超过 daemon 配置的执行时长上限 | 缩小 issue 范围，或调 daemon 的 `agent_timeout` |
| `iteration_limit` | 触到单次运行的迭代上限 | 缩小 issue 范围 |
| `agent_blocked` | 智能体报告它推进不了 | 按它评论里要的东西提供 |
| `api_invalid_request` | 平台 API 收到非法请求 | 重试；反复出现则上报 |
| `codex_semantic_inactivity` | Codex 长时间没有有意义的输出，判定卡死 | 重试，或调 Codex 的空闲阈值 |

**工具侧（`agent_error.*`）**：`provider_auth_or_access`（401/403）、`provider_quota_limit`（402）、`provider_capacity_or_rate_limit`（429/529）、`provider_server_error`（5xx）、`provider_network`、`model_not_found_or_unavailable`、`context_overflow`、`missing_config`、`runtime_missing_executable`、`runtime_version_unsupported`、`process_failure`、`empty_or_unparseable_output`、`agent_timeout`、`unknown`

### 3.4 自动重试规则

**会**自动重试的（仅限挂了 issue 或 chat 的 run）：

| 失败原因 | 尝试上限 |
|---|---|
| runtime 掉线 | 默认 2 次（首次 + 1 次重试） |
| daemon 重启后回收 | 2 |
| 平台判定的执行超时 | 2 |
| Codex 长时间无有意义输出 | 2 |
| skill 包下载失败 | 2 |
| 工具侧网络中断 | 最多 3 次，最后一次延迟约 5 秒 |

**不会**自动重试的：认证、配额、配置、模型类错误，以及 `cancelled`。这些要先把原因修掉再手动重试。

> ⚠️ **autopilot 的 "run only" 模式不自动重试。**

### 3.5 并发与目录锁（本次翻车的高嫌疑项）

- 单 agent 默认 **6 并发**；单 daemon 默认 **20 并发**。到上限后新 run 排队
- **`waiting_local_directory`**：本地目录处于 **`in_place`（Direct）模式**时，**同一目录同时只能跑一个 run**，其余排队等锁。
  - 官方解法：目录是 git 仓库时改成 **`worktree`（Parallel）模式**，每个 run 拿自己的 worktree，排队消失
  - 我们的场景（需求分析只读、多仓 git 结构）未必能用 worktree ⇒ 现实做法是**收敛并发**或**给不同 agent 分不同目录**
  - 这个目录互斥锁只在 daemon 内存里，没有锁文件。怀疑锁状态脏了 ⇒ `multica daemon restart` 释放
- 改负责人 / 改状态**不会**中断已经开始的 run；但**会取消排队中的 task**。要中断只能去 execution log 里 stop
- **run 失败后不会自动唤醒负责人** ⇒ 会静默躺住，需要人手动 retry 或 @ 一下

### 3.6 回退约定

系统只保证**成功的 run** 才能恢复。手动重试的行为：

- 重试调用的是**当时处理那个 run 的 agent**，即使 issue 已经改派给别人，也不会切到新负责人
- 重试**尽量保留**上一个 run 已经写进本地目录的文件；会话还安全且同一 runtime 接手时，会**继续上一个会话**
- 会污染会话的错误（context overflow、非法请求）⇒ 在原有工作目录上开新会话
- `multica issue rerun <issue-id>` ⇒ 用**当前**负责人，全新会话 + 新工作目录

## 四、易踩清单（对着每条自查）

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 把 issue 指派给成员来"派活" | 用 Squad Roster 的 mention 链接 @ 它。**负责人永远是小队** |
| 2 | 成员交回时 @ 队长 | 发**不带任何 @** 的顶层评论 |
| 3 | 需要人介入却在 issue 里干等 | **@人类负责人**（显式 @ 会路由给人，不惊动队长） |
| 4 | 中途进展发成普通评论 | 用 `/note` 开头，或只写进运行输出 |
| 5 | 一回合发多条评论 | 合并成一条（平台会合并/排队） |
| 6 | 自造状态名 | 用内置 `todo/in_progress/in_review/done/blocked` |
| 7 | 靠解析评论判进度 | 把阶段写进 **label**，读 label |
| 8 | 人审打回用 `/note` 或 `@all` | 必须显式 **@队长 / @小队**，否则队长不醒 |
| 9 | 看到 `todo` 就当新单 | 若**已有阶段 label**，那是失败回退，按 label 继续 |
| 10 | 同一件工作既建 `todo` 子任务又 @ 同一个 agent | **二选一**，否则并行跑两次 |
| 11 | 子任务只推到 `in_review` | 阶段推进靠"子任务全部 **done/cancelled**"，不 done 永远不触发 |
| 12 | 升级 Multica 只升服务端 | daemon 也要逐个升；改 runtime profile 参数要**重注册 daemon** |

## 五、还没实测 / 官方文档自相矛盾的地方（别当定论）

1. **改负责人对运行的影响**：官方文档说"改负责人不中断已开始的 run"，社区逆向源码说"改负责人会取消该 issue 现有 tasks"。合理解释是**已认领的 run 不停、排队中的 task 被取消**。未实测。
2. **label 能否被 agent 稳定读到**：本设计让队长"读 label 判阶段"。issue 的"字段"理论上包含 label，但没有官方明文保证注入。已做降级：读不到 label 时退化为读最近一条【派单】评论。**建议第一次实跑时确认一下。**
3. **内置 `blocked` 在你们这个版本是否可用**：内置 7 状态里列了它，但你们的 workspace 若做过状态定制需要确认。
4. **成员提示词里的"不带 @ 交回"是否真的每次都能回落**：机制上成立，但成员是模型，可能"礼貌地"写上 @队长。**这条要在实跑日志里看一两次才能确认。**
5. **`multica squad activity` 的确切参数形态**：官方文档与协议文本给的是 `<issue-id> <outcome> --reason "..."`。若报参数错误，用 `multica squad activity --help` 核对。
