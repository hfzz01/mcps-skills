# 02 · 模型使用约束

## 1. 硬约束（违反即编译失败或视为方案外）

1. **只允许五个模型**：`GLM5.2`、`deepseekv4.1-flash1017`、`MiniMax-M3`、`Qwen3.7-max`、`Qwen3.7-plus`。
   禁止引入清单外任何模型——包括视觉/VL、OCR、embedding、rerank、代码专用、外部商用 API 模型。
2. **工具侧零模型调用**：`prism/engine/*` 不 import 任何 SDK、不读取任何 API key / token、
   不发起任何出网 HTTP 请求。模型调用只发生在**内网 codeagent 会话内部**，由公司已有的调用通道完成。
3. **模型唯一产出物是蓝图 JSON**：模型不写 HTML、不写 CSS、不写 JS、不改 `foundry/` 下任何文件。
   蓝图里若出现色值、字号、间距、圆角等样式描述，链接器判为 error 并中止铸造。
4. **截图不交给模型识别**：清单内没有明确的视觉模型，且本方案禁止把图像交给模型做语义判断。
   截图只走 `extract-image.mjs` 的确定性像素计算；语义信息来自需求文档与人工补充。
   即便个别模型具备多模态能力，也**不得**用于一致性判定或页面结构推断。
5. **一致性判定不交给模型**：组件合法性、跳转可达、样式同源、批量结构一致全部由 `linker.mjs`
   确定性完成。模型不参与"这页像不像"的判断。
6. **模型声明可审计**：蓝图可选 `generator.model` 字段，值必须在白名单内；
   链接器校验并写进一致性报告。不声明也能编译，但报告会标为「未声明」。
7. **降级只在清单内**：某个模型不可用 / 超时 / 输出不合格时，换清单内另一个模型重跑该环节，
   不补外部模型、不降级到"人工手写 HTML"。
8. **不引入新依赖**：不因为模型能力不足而引入需要 API key 的库或在线服务。

## 2. 关于模型能力数据的诚实声明

**不确定项**：这五个模型在内网的具体部署形态、上下文窗口、是否多模态、并发与限流策略，
本机没有可靠数据，本方案**不做臆测，也不按厂商宣传参数分工**。

因此分工是按**任务角色与失败成本**设计的：所有环节只要求一项能力——
「读一份中文需求文档 / 一份规格说明 → 输出符合 schema 的结构化 JSON」。
这是五个模型都能胜任的共同分母；具体哪个模型跑哪个环节，可在内网实测后互换，
不影响方案其它部分。**把方案的正确性押在某个模型的特定能力上，是这类工具最常见的翻车原因，这里刻意避开。**

## 3. 分工表（角色分派，可互换）

| 模型 | 承担环节 | 输入 | 输出 | 失败回退 |
| --- | --- | --- | --- | --- |
| `Qwen3.7-max` | 存量优化主蓝图：需求文档 + 存量基线 → 差异蓝图 | 需求文档、变更清单、页面基线说明 | `blueprints/asset-ledger.json` | 换 `Qwen3.7-plus` 重跑 |
| `GLM5.2` | 存量页补齐：详情/编辑/抽屉等配套页面蓝图 | 需求文档、`docs/04` 组件白名单 | `blueprints/asset-detail.json` | 换 `Qwen3.7-max` 重跑 |
| `Qwen3.7-plus` | 新增功能主蓝图：多步流程、状态剧本、跳转图 | 新增功能需求文档 | `blueprints/inspection-plan.json` | 换 `MiniMax-M3` 重跑 |
| `deepseekv4.1-flash1017` | 轻量补全：看板字段、状态文案、标签枚举、批量矩阵条目 | 已有蓝图 + 需求文档片段 | `blueprints/inspection-result.json` 等 | 换 `GLM5.2` 重跑 |
| `MiniMax-M3` | 批量场景：需求矩阵 → 统一模板蓝图的语义确认 | 批量需求文档 + 矩阵 | `blueprints/batch/_template.json` 的字段映射说明 | 换 `Qwen3.7-max` 重跑；矩阵展开本身由 `expand.mjs` 确定性完成 |

> 注意：批量展开**不是模型逐页写 12 份**。模型只确认一次模板语义，
> 12 份蓝图由 `expand.mjs` 用确定性公式从矩阵生成。这正是批量一致性的来源，
> 也把模型调用次数从 12 次压到 1 次。

本仓库示例里五个模型都各出现了一次（见 `dist/consistency-report.md` 的「模型使用审计」表），
用于证明白名单校验生效；实际内网可按可用情况重新分派。

## 4. 调用发生在哪里、绝不发生在哪里

```
[内网 codeagent 会话]  ← 模型只在这里被调用
   需求文档 / 基线说明 / 组件白名单
        ↓ 模型输出
   blueprints/*.json  （纯声明式，零样式）
        ↓
[Prism 引擎 · 无模型]  lint → expand → compile → dist/
        ↓
[浏览器 · 无模型]     用户点击 / 输入 / 切状态 / 跳页
```

**绝不调用模型的环节**：
- 样式宪章提取（像素量化 / computedStyle / 变量扫描都是确定性代码）
- 组件渲染（契约里是写死的 render 函数）
- 一致性校验与结构指纹（哈希计算）
- 批量展开（确定性公式）
- 原型运行时（纯 DOM 事件委托）
- 任何验收与报告生成

## 5. 编译期如何强制

| 约束 | 强制方式 | 位置 |
| --- | --- | --- |
| 只用五个模型 | `ALLOWED_MODELS` 白名单，蓝图 `generator.model` 不在表内 → error | `engine/linker.mjs` |
| 模型不写样式 | 遍历蓝图所有字符串，命中 `#hex` / `rgb()` / `font-size:` / `margin:` / `color:` → error | `engine/linker.mjs` |
| 模型不造组件 | 组件名必须命中 `CONTRACTS` 白名单，props 通过类型校验 | `engine/linker.mjs` |
| 模型不改契约 | `foundry/` 是人工维护目录，模型输出只有 `blueprints/`；契约哈希写进报告便于比对 | `engine/compiler.mjs` |
| 模型不碰交互脚本 | 页面里没有内联脚本，只有 `assets/runtime.js` 一份；自检扫描断言 | `engine/selftest.mjs` |

## 6. 失败处置

| 现象 | 处置 |
| --- | --- |
| 模型输出不是合法 JSON | 换清单内另一个模型重跑该环节；不要把半截输出手工补成 HTML |
| 模型输出里带了 CSS / 色值 | 链接器报错并指出字符串位置；让模型重出蓝图，不要改宪章去迁就 |
| 模型编造了不存在的字段/页面 | 链接器按组件白名单与跳转可达性拦下，报告会点名 |
| 某模型整体不可用 | 按第 3 节回退列换模型；**不补外部模型** |
| 需求文档本身缺状态描述 | 先补需求文档，再让模型出蓝图；这不属于模型能力问题 |

## 7. 审计

`dist/consistency-report.md` 会列出每个模型产出的蓝图数、允许清单、以及
"工具侧不调用任何模型"的事实陈述；`dist/manifest.json` 记录宪章哈希、契约哈希与页面指纹。
内网留存报告即可追溯"哪一页是哪个模型出的蓝图"，不需要额外系统。

## 8. 一句话总结

模型负责**意图**（要什么页面、什么数据、什么跳转），编译器负责**一致性**（长什么样、怎么交互）。
把这两件事分开，模型能力强弱就不再是原型质量的瓶颈。
